01 What the system does

A ticketing platform where every organization runs its own isolated workspace — members, roles, tags, projects, and tickets never leak across tenants.

Dual-mode accounts

A user can work in "Personal" mode (their own standalone tickets, no org) or create/join an Organization. Chosen once at onboarding.

Real auth

Email/password signup with mandatory email verification, Google OAuth, httpOnly JWT session cookie.

Multi-tenant organizations

Each org has its own settings, seat/usage capacity limits, roles, tags, and projects — fully isolated from every other org.

Granular RBAC

Roles are a named bundle of fine-grained rules (e.g. ticket.view.included) across 9 categories — not a fixed admin/member split.

Tickets & requests

Org tickets, personal tickets, and client-submitted "requests" that an org member reviews and either approves (becomes a real ticket) or rejects.

Invite-only membership

Members join only by invite (token + expiry, resend with cooldown). An invited-only account can never create its own organization.

Activity & notifications

Every mutation writes an append-only activity-log entry; a notification bell streams live updates over SSE plus an unread count.

Attachments & idempotency

Ticket/request attachments go straight to S3. Mutating requests honor an Idempotency-Key header to make retries safe.

03 Roles & permission categories

A Role is just a named set of Rules. Every org gets its own roles (cloned from org-less templates), so "Superadmin" in one org is a separate, independently-editable row from "Superadmin" in another.

Category Example rules
Organization organization.update.basicInfo · organization.change.ownership
Member member.invite · member.update.role · member.view.owner
Role role.add · role.update · role.remove

05 Core flows

The five user journeys that define how the system actually gets used, in the order a new org typically hits them.

Flow 1 Signup, verification & onboarding

Flow 5 Ticket request → approval

A "request" is how someone without ticket-create rights (or an external client) gets a ticket started — an org member with approval rights decides.

06 Deployment & CI/CD

  • Frontend — Vercel, Auto-Deploy on push to main. GitHub Actions runs lint/typecheck/tests/build, then calls the Vercel CLI, which blocks until the deploy is actually ready and fails the job if it isn't.
  • Backend — Render, Auto-Deploy on push to main. GitHub Actions runs the same gate (security audit, typecheck, lint, unit tests with a coverage threshold, build), then polls Render's API for that exact commit's deploy until it's live — or fails the job with Render's real error if it isn't.
  • Database — PostgreSQL, migrated via prisma migrate deploy.
  • Attachments — uploaded directly to S3; the backend never stores files on its own disk (a Render free-tier redeploy wipes local disk).
